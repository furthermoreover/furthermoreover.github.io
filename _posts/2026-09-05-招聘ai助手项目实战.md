> 今年夏天，我从零做了一款面向 HR 的本地招聘管理小应用：**Recruit AI Assistant（招聘 AI 助手）**。它最核心的卖点是「对话式指挥」——不点按钮，直接用自然语言吩咐 AI，它就能帮你完成候选人录入、查询、更新状态、生成沟通话术。

这篇文章记录它的设计思路、关键实现和踩过的坑。

## 为什么做这个项目

传统招聘管理有几个痛点：

- 候选人信息散落各处，手动填表录入，**重复录入**家常便饭
- 想查「上周投了算法岗、还没面试的候选人」要手动筛 Excel
- 给候选人发沟通话术，每封都要重新组织语言

于是我想：能不能让 AI 直接操作那张台账表格？**用户动嘴，AI 动手。**

## 功能一览

- **对话式指挥**：自然语言 → LLM 函数调用 → 操作 Excel 台账
- **简历智能解析**：上传 PDF / Word / TXT，自动抽取姓名、电话、期望薪资、到岗时间
- **候选人台账**：查重检测、下拉选择、状态更新（面试时间悬浮选择）、删除带确认弹窗
- **数据统计**：候选人总数、各岗位 / 渠道分布
- **多用户系统**：注册 / 登录，每用户数据独立
- **模型切换**：前端下拉一键切换 12 个 LLM 模型
- **打包 exe**：双击即用，无需装环境

## 架构设计

```text
┌──────────────┐   代理转发   ┌──────────────────┐   函数调用   ┌───────────┐
│ 前端 app.py   │ ──────────► │ 后端 FastAPI:8010  │ ──────────► │  LLM API  │
│ (单页, 7860)  │            │  Excel 台账存储    │             └───────────┘
└──────────────┘            └──────────────────┘
                                    │
                     data/<用户>/recruit_record.xlsx
```

- 后端：FastAPI，监听 8010
- 前端：单页应用，监听 7860，所有 `/api/*` 请求代理转发到后端
- 数据：Excel（openpyxl / pandas），每个用户一个独立台账文件

**为什么选 Excel 而不是数据库？** 因为 HR 最终要的就是一张能直接打开、筛选、发给别人的表格。Excel 既当数据源，也当交付物，一举两得。

## 核心实现

### 1. 对话式指挥：LLM 函数调用

核心是一个循环：把系统提示 + 最近对话发给模型，带上 `tools` 定义，模型决定调用哪个工具、给什么参数，后端执行后再把结果喂回去，最多循环 12 轮：

```python
# /agent_chat 对话式指挥（简化）
msgs = [{"role": "system", "content": sys_prompt}]
# 只保留最近 6 条，避免历史过长拖慢响应
recent = [m for m in messages if m.get("role") in ("user", "assistant") and m.get("content")][-6:]
msgs += recent

for _ in range(12):
    resp = client.chat.completions.create(
        model=CURRENT_MODEL, messages=msgs,
        tools=AGENT_TOOLS, tool_choice="auto", max_tokens=512,
    )
    msg = resp.choices[0].message
    if not getattr(msg, "tool_calls", None):
        return {"reply": msg.content or "", "tool_calls": tool_log}  # 模型已给出最终答复
    # 逐个执行工具调用，把结果追加回消息里再继续
    ...
```

系统提示里列出可用工具，让模型自己组合：

```text
你是「招聘AI助手」，帮HR管理候选人台账。工具：
list_candidates(列候选人)、get_all_records(台账明细)、get_jobs(岗位)、
get_stats(统计)、gen_talk(话术)、parse_resume_add(简历入库)、
update_candidate_status(更新状态)、delete_candidate(删除)。
按用户指令自主调用工具，删除前先确认，最后用简短中文汇报结果。
```

值得一提的细节：**模型不支持 tools 时自动降级为普通问答**，保证老接口也能聊起来。

### 2. 简历解析入库：让 LLM 输出严格 JSON

上传简历后，用「只输出严格 JSON」的系统提示让模型抽取结构化字段：

```python
sys_prompt = """
你是简历信息抽取助手。只输出严格JSON对象，不要输出任何其他文字。
字段一共4个：candidate_name（候选人姓名）、phone（联系电话）、
expect_salary（期望薪资）、available_time（到岗时间）。
识别不到的字段，值填写字符串“未获取”。
输出示例：{"candidate_name":"张三","phone":"13800138000",...}
"""
```

抽取结果入库前还会做**查重**：姓名相同、或手机号相同（且非空）即视为同一候选人，自动提示用户「继续新增 / 更新已有 / 强制新增」。

### 3. 多用户隔离：PBKDF2 + token

每个用户一个独立台账文件 `data/<用户名>/recruit_record.xlsx`，密码用 PBKDF2-SHA256 加盐哈希，登录发放 token：

```python
def _hash_pwd(pwd, salt):
    return hashlib.pbkdf2_hmac("sha256", pwd.encode(), salt.encode(), 100000).hex()
```

### 4. 模型切换：启动时探测，前端下拉即换

启动时从 `/models` 接口拉取账号可用模型（失败则回退内置候选列表），前端一个下拉框切换，**无需重启**：

```python
AVAILABLE_MODELS = _fetch_available_models()  # 回退列表含 qwen / glm / deepseek 等

@app.post("/model")
def set_model(body):
    global CURRENT_MODEL
    if body.get("model") in AVAILABLE_MODELS:
        CURRENT_MODEL = body["model"]
```

## 踩过的坑

1. **ConnectionError：8010 连接被拒** —— 前后端分离，前端起好了但后端没起来。排查后统一由启动器保证先后端、后前端的顺序。
2. **PyInstaller 打包后台账读空** —— exe 里模块的 `__file__` 指向 `_internal`，数据路径全错。解法：启动器注入环境变量 `RECRUIT_DATA_DIR` 指向 exe 同目录的 `data/`。
3. **UI 被「太丑」劝退** —— 一开始用 Gradio，被嫌弃后重写成单页应用，漂亮多了，也顺便支持了更细的下拉、悬浮窗、确认弹窗。

## 收获

从需求到落地，最大的体会是：**AI 应用的边界往往不是模型能力，而是你愿不愿意把「最后一公里」做好**。对话式指挥、Excel 即交付、打包成双击即用的 exe——这些才是它真正能落地的原因。
